# 目录结构

> 何时读本文：需要判断某个目录要不要建、或某篇文档该放到哪里时。

## 这是默认规则，不是铁律

下面这套结构是**通用的、规范性的指导**，不是必须照搬的模板。两个方向都允许偏离：

- **减法**：不需要的目录不建。没有真实内容的目录一律不建，空目录和占位 README 都是负债。
- **加法**：出现这里没提到的文档类型时，**新建目录是正当的**，见下文「加法：新文档该放哪」。

偏离的前提是**有理由、且能说清理由**，而不是随手决定。判定规则见下。

## 结构总览

```
project/
├─ AGENTS.md                 # 必备 · AI 路由入口，不放规范正文
├─ README.md                 # 必备 · 项目是什么、怎么跑起来
├─ CHANGELOG.md              # 按需 · 与 docs/releases/ 二选一
└─ docs/
   ├─ README.md              # 必备 · 文档中心：索引 / 元数据规范 / 事实源
   ├─ guides/                # 按需 · 指南类：怎么做
   │  ├─ user/               #   面向使用者：安装、使用、配置
   │  ├─ developer/          #   面向外部接入方：扩展、SDK、插件开发
   │  ├─ faq/                #   高频问题
   │  └─ reference/          #   配置项、环境变量、事件与钩子索引
   ├─ development/           # 按需 · 与项目实际开发流程有关
   │  ├─ standards/          #   必须遵守的约定，被 AGENTS.md 引用
   │  ├─ architecture/       #   当前有效的系统设计
   │  ├─ decisions/          #   历史技术决策记录（ADR）
   │  ├─ rfcs/               #   尚未定稿的提案
   │  ├─ requirements/       #   已冻结的需求基线
   │  └─ design/             #   例：UI/UX 等设计类文档，规模大了才拆出来
   ├─ operations/            # 按需 · 运维类
   │  ├─ testing/            #   测试策略
   │  └─ performance/        #   压测与调优记录
   ├─ api/                   # 按需 · 对外提供的接口契约
   ├─ templates/             # 按需 · 各类文档的模板
   ├─ assets/                # 按需 · 文档引用的图片与附件
   └─ releases/              # 按需 · 版本归档
```

## 必备（不建则体系不成立）

| 路径 | 职责 |
|---|---|
| `README.md` | 项目是什么、如何运行、去哪找更多。见下方「根 README 与文档中心的分工」 |
| `AGENTS.md` | AI 路由入口，只放路由与硬约束，不放规范正文 |
| `docs/README.md` | 文档中心：入口导航、目录职责、元数据规范、事实源优先级、不纳入索引的目录清单 |

### 根 README 与文档中心的分工

两者都是入口，但读者不同。边界定死，否则会各自膨胀成"什么都放一点的首页"：

| | 根 `README.md` | `docs/README.md` |
|---|---|---|
| 读者 | **刚到仓库的人**——可能是使用者，也可能是贡献者 | 已经决定读文档的人 |
| 回答 | 这是什么、怎么跑起来、去哪找更多 | 文档怎么组织、元数据规范、事实源优先级 |
| 索引 | **不做索引**，只一次跳转到 `docs/` | 索引整个 `docs/` |
| 额外约束 | 会被包管理器与代码托管首页**直接展示** | 只在仓库内看 |

最后一行是根 README 独有的约束：包页与仓库首页只渲染它的开头几行，所以**安装与运行命令必须靠前**，
先讲原理或架构等于没写。分发渠道不同，形态也该不同——通过包管理器分发的项目要比内部工具更克制。

**根 README 不索引文档。** 一旦它也列文档清单，就有了两处需要同步维护的索引，
而且必然会分叉。文档的事交给 `docs/`。

## 按需（有真实内容才建，空目录不建）

| 路径 | 职责 | 启用条件 |
|---|---|---|
| `docs/development/standards/` | 必须遵守的编码、Git、发布等约定 | 用户要求添加规范 |
| `docs/guides/user/` | 面向使用者的安装、使用、配置说明 | 存在非开发者使用者 |
| `docs/guides/developer/` | 面向外部接入方的扩展开发说明 | 存在插件、SDK 或扩展开发方 |
| `docs/guides/faq/` | 高频问题与解答 | 问答累积到 5 条以上 |
| `docs/guides/reference/` | 配置项、环境变量、事件与钩子的索引 | 这类内容超过一页 |
| `docs/development/architecture/` | 当前有效的顶层设计、核心交互、状态流转 | 系统有可描述的顶层结构 |
| `docs/development/decisions/` | 历史技术决策及其取舍 | 出现第一个「以后会被问为什么」的决策 |
| `docs/development/rfcs/` | 尚未定稿、需要先讨论的提案 | 有需要先达成一致的变更 |
| `docs/development/requirements/` | 已冻结的需求基线 | 需要验收依据或多人协作 |
| `docs/development/workflow.md` | 项目实际的分支、发布与 CI 流程 | 与默认约定不同时 |
| `docs/operations/testing/` | 测试策略与用例组织 | 测试策略超出规范里几句话 |
| `docs/operations/performance/` | 压测方法、指标与调优记录 | 有性能指标或调优记录 |
| `docs/api/` | 对外提供的接口契约 | 有给别人调用的接口 |
| `docs/templates/` | 各类文档的模板 | 文档类型多到需要统一格式 |
| `docs/assets/` | 文档引用的图片、图表与附件 | 文档里有非文本资源 |
| `docs/releases/` | 版本归档与验收证据 | 有对外发布版本，且与根 `CHANGELOG.md` 二选一 |

## 加法：新文档该放哪

结构不可能穷举所有文档类型。遇到没提到的类型时，按下面的顺序判定。

**判据不是「主题」，而是「读者 + 生命周期 + 变更频率」。** 同一主题的文档，读者或寿命不同就该分开放。

1. **现有目录的职责能覆盖它吗？** 能就直接放进去——不要因为名字不完全贴切就新建目录。
2. **它只是已有维度的细分吗？** 初期一律并入现有目录。目录数量本身是成本。
3. **它的读者或生命周期与现有目录不同吗？** 只有这一条成立，才是新建目录的正当理由。
4. **确认要新建**：小写 kebab-case 的类别名；**必须同时写该目录的 README 说明职责**。没有 README 的新目录不是归类，是堆放。

用「UI/UX 设计文档」验证这套规则——同一个主题，三个不同归属：

| 文档性质 | 归属 | 为什么 |
|---|---|---|
| 当前界面设计规范（长期有效、少变） | 先并入 `development/architecture/` | 与架构同读者、同寿命 |
| 某次改版的探索稿（短命） | `development/rfcs/` | 生命周期不同 |
| 给使用者的界面操作说明 | `guides/user/` | 读者不同 |

## 规模驱动的演化

「初期并入、规模大了再拆」要写成可观察的信号，而不是靠感觉。出现下列任一情况，就该考虑拆分：

- 某目录的文档数达到 8–10 篇，且能清楚地分成两组
- 目录 README 的索引表超过一屏
- 同一目录里出现了两种不同的读者，或两种明显不同的生命周期

拆分动作**就是一次整理（见 `retrofit.md`）**：建新目录 → `git mv` → 修相对链接 → 更新两个目录的 README → 在 `docs/README.md` 留映射表。不要随手搬。

以 UI/UX 为例：`development/architecture/` 里累积到一定规模后，升格为与 architecture 并列的 `development/design/`——读者与寿命相近，所以是并列而不是子目录。

## 硬规则

1. **不建空目录、不建占位 README。** 一个目录被创建，当且仅当它至少有一篇真实内容。
2. 项目内的 `docs/templates/` 是给写文档的人用的模板；本 skill 的 `assets/templates/` 是生成这些模板的来源。两者不混用。
3. `docs/releases/` 与根 `CHANGELOG.md` 二选一：对外发布且需归档验收证据用 `releases/`；纯迭代记录用 `CHANGELOG.md`。
4. 单篇文档不单独建目录。
5. **每个非空目录必须有 `README.md`**，且其索引表由生成器维护（见 `automation.md`），不手写。

## 生成时的做法

- **必备集**直接创建。
- **按需集**先算出「拟建目录 + 职责 + 启用理由」，一次性交给用户确认，确认后才建。
- 目录 README 的索引表**由生成器产出**，不在生成阶段手写。
- 根 `README.md` 用 `_root-readme.md` 生成；项目已有的则**一字不改**。
- 根 `CHANGELOG.md` 与 `docs/releases/` 归发布记录工具，本流程不手工创建。
- 模板里的 `<!-- gen-note: ... -->` 是**生成指令**，按它做完操作后必须一并清除。
