# 自动化生成

> 何时读本文：需要决定项目的索引怎么维护、发布记录怎么产出时。

## 默认自动化，手动兜底

文档体系里有两类内容**天然容易腐烂**，因为它们必须跟着别的东西一起变：

| 内容 | 依赖什么变化 | 手工维护的结局 |
|---|---|---|
| 目录索引表 | 文档的增删改 | 文档改了、索引忘了，然后没有人再相信索引 |
| 版本与发布记录 | 提交历史与版本号 | 第三个版本之后开始说谎 |

所以规则是：**这两类默认由工具生成**；手写只在用户明确要求、或项目正在迁移途中时才允许。

**「让 AI 帮忙手写」不算自动化。** 它仍然是手动维护，只是换了执行者，而且比人更容易忘记。

## 索引：不需要选型

`gen_index.py` 是零依赖的，任何技术栈直接可用，没有选型问题。
标记约定与命令见分片 `assets/automation/index-generation.md`。

## 发布记录：按栈选分片

读 `assets/automation/` 下的分片，按各自 `applies_when` 挑选：

| 分片 | 适用 |
|---|---|
| `changelog-node.md` | Node，且以 npm / pnpm / yarn 工作区组织 |
| `changelog-generic.md` | 其他任何技术栈，提交信息遵循约定式格式 |

**没有匹配的分片时：不启用 `docs/releases/`，CHANGELOG 也不强求。**
宁可暂时没有发布记录，也不要留一份手工维护、注定过期的。

## 文档站

`docs/` 的结构本身就是为文档站准备的源。站点侧边栏应交给文档站自己生成
（例如 VitePress 的 sidebar 自动生成），**不要在站点配置里再抄一份目录清单**——
那又是一处会脱节的手工索引。

## 加一门栈要做什么

1. 在 `assets/automation/` 下新建 `<用途>-<栈>.md`
2. 写 frontmatter：4 个必填字段 + `applies_when`
3. 写清四件事：装什么、怎么初始化、日常命令、与发布流程如何衔接
4. 拷入项目时**去掉栈后缀**，落为 `docs/development/standards/<用途>.md`

不需要改 `SKILL.md`，也不需要注册——运行时枚举目录发现。
