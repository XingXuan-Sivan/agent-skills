# ADR 维护规则

> 何时读本文：要写新的 ADR，或发现 ADR 内容与当前实现不一致时。

## 前提认知

ADR 回答的是「**当初为什么这么定**」，不是「现在是什么样」。后者由 `architecture/` 负责。

这也是为什么事实源优先级里 ADR 排在最后一位——它本来就不是现状的权威。理解这一点，绝大部分「实现和 ADR 对不上」的焦虑会自动消失：**该改的是架构文档，不是 ADR。**

## 判定表

| 实际发生了什么 | 该改哪里 | 是否新开 ADR |
|---|---|---|
| 决策本身变了（方案变化、约束变化） | 新 ADR，旧的标 `superseded` | **必须** |
| 决策未变，只有「现在长什么样」漂了（类名、路径、配置项） | 改 `architecture/` | 不用 |
| 决策未变，描述不精确或有歧义 | ADR 内追加带日期的补充 | 不用 |
| 纯笔误、失效链接、符号重命名 | 原地修改 | 不用 |

日常开发中遇到的小修改，绝大多数落在第二行和第三行。

## 允许的操作

- 修正笔误、失效链接、符号重命名 → 原地改
- 决策未变但描述不足 → **只允许追加**，格式如下：

  > 补充（2026-10-01）：实现中因 X 约束，配置前缀实际为 `app.panel`，决策本身未变。

- `status` 随现实更新：`active → deprecated`，或被替代时 `active → superseded`

## 禁止的操作（红线）

- **静默改写已有条目，让它看起来「一直就是那样」**
- 删掉当初被否掉的选项与理由

真正该守的线是「禁止静默改写」，而不是「禁止任何改动」。写成后者，规则会因不近人情而被整体忽略——那比没有规则更糟，因为它同时失去了可读性和可信度。

## 配套约定

- 被替代的 ADR 必须在正文里链接到替代它的那篇（校验脚本会检查）
- 被否决的提案用 `status: rejected` 保留，不要删除——否决理由本身是资产
- 每篇 ADR 在提交时附带上文「判定表」中对应的那一类变更说明，便于审查者判断是否越界
