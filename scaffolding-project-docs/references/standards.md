# 规范分片模型

> 何时读本文：需要决定项目该用哪些规范，或想把项目里沉淀的规则回写到模板时。

## 三维分片

规范以独立文件分片存放，每个文件只讲一个维度：

| 维度 | 说明 | 例子 | 必备性 |
|---|---|---|---|
| 通用内核 | 任何项目都适用 | `universal.md` | **必备** |
| 技术栈分片 | 与该栈无关的规则不该混进来 | `backend-java.md`、`frontend-vue.md`、`python.md` | 命中才拷 |
| 领域分片 | 与栈无关但需要专门展开 | `git.md`、`testing.md`、`security.md` | 按需 |

判据很简单：**一条规则换个技术栈就不成立，它就不是通用内核。**

## 分片自描述

分片在自己的 frontmatter 里声明适用条件：

```yaml
---
title: Git 分支与提交规范
type: standard
status: active
summary: 提交格式、分支模型、版本与发布流程、仓库卫生，以及 AI 协作下的约束。
applies_when: 项目使用 Git 管理版本
---
```

**拷入项目时删除 `applies_when`**，其余字段保留——项目已经决定用它了，留着是噪音。

## 规范的三种来源

整理既有项目时，规范不该只有"拷模板"一条路：

| 来源 | 适用场景 | 做法 |
|---|---|---|
| ① 拷 skill 分片 | 新项目、无既有惯例 | 直接拷贝并去掉 `applies_when` |
| ② 从现状反向提取 | 项目已有稳定惯例 | 读提交记录、分支命名、目录结构，把实际做法写成规范 |
| ③ 合并 | 有部分惯例，想补全 | 项目已有规则与分片去重合并，冲突处**以项目为准** |

来源②往往才是有既有项目最常用的路径：**项目早有一套事实上的规范，只是没写下来。** 把它读出来、写成文、再补上缺的，比拿模板硬盖要好得多。

来源②的产出与来源①格式完全一致，区别只在于规则文字来自项目现状而非模板。

## 新增一个分片

1. 在 `assets/standards/` 下新建 `<名字>.md`
2. 写 frontmatter：4 个必填字段 + `applies_when`
3. 正文用 H1 标题 + 分节列表；一条规则一行，**不要写成散文**
4. 确认内容与本项目无关——不要出现具体产品名、包名或团队私有工具名

不需要改 `SKILL.md`，也不需要注册。运行时通过枚举目录发现。

## 回写模板

当项目里沉淀出值得复用的规则时，可以把它回写到 skill 的分片模板。**触发起点是用户明确要求**，不自动执行。

1. 读项目 `docs/development/standards/*.md` 与 skill `assets/standards/*.md`
2. 做条目级 diff，找出只存在于项目侧的规则
3. **只追加、不删除、不覆盖**：把新条目按语义归入对应分片
4. 输出「拟追加条目 + 目标分片」清单，等用户确认后再写入
5. 若某条目与分片内既有条目语义冲突，**不自动合并**，单独列出让用户裁决

回写同样遵守不静默改写的约束。
