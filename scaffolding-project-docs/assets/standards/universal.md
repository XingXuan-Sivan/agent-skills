# 通用开发规范

以下约定与具体技术栈无关，任何项目都适用。

## 架构与设计

- 代码须遵循高内聚低耦合原则，职责边界清晰，杜绝重复逻辑，以保障系统的优雅性、规范性及可演进能力。
- **约定优于配置**：默认行为应基于通用约定，仅在需要覆盖默认行为或存在特殊业务场景时才显式配置。通过减少不必要的配置项，降低维护成本。
- 设计文档只写抽象且持久的内容——顶层架构、核心交互、状态流转、框架性代码；仅在发生重大架构调整时更新；被修改时不保留历史设计内容。

## 配置与常量

- 横切关注点（如过滤器、拦截器）应基于基路径配置，符合开闭原则。
- 所有通用路径及配置项必须收敛至常量或配置文件，严禁硬编码或重复定义。
- 配置中的前缀使用**领域或能力名**，禁止写死项目名或产品名——前缀一旦绑定产品，配置就无法跨项目复用。

## 代码与注释

- 通用逻辑必须封装为独立的工具类或模块；开发时优先复用现有工具，严禁在业务代码中重复造轮子。
- 注释保持与现有代码风格一致，只描述代码意图，严禁包含 `@since`、`@author` 等元数据标签及修改历史记录。
- 注释中不提及具体项目名或产品名。
- 用户可见的提示语与日志信息使用中文。

> 最后一条属于团队偏好，与项目实际受众不符时整条删除。

## 交付质量

- **零技术债**：严禁遗留临时代码或未完成的逻辑。
- **全局清理**：重构或修改完成后必须全局扫描，删除不再使用的旧目录和文件。
- **文档一致性**：同步更新设计文档与用户文档，确保内容与实现完全一致；严禁编造未实现的设计；保持文档整体风格统一。

## 文档

- 用户文档须随功能变更同步更新，确保描述与产品界面、操作流程及实际行为严格相符。
- 历史决策记录（ADR）的维护规则：决策内容不可修改；允许修正笔误与失效链接，允许追加带日期的补充说明；**禁止静默改写已有条目**，让它看起来一直就是那样。详见项目 `docs/development/decisions/README.md`。
