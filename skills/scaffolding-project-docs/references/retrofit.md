# 整理既有文档：盘点与纳管

> 何时读本文：项目已有 `docs/` 或散落 Markdown，需要建立、完善或重整文档体系时。

## 核心原则

**只出方案，逐项确认后执行。** 默认不移动、不重命名、不改写任何已有正文。

整理既有文档是破坏性操作：移动文件会打断相对链接、割裂版本控制历史的可读性、作废别人收藏的路径。所以激进度的选择权在用户手上，不在执行者手上。

## 第一步：只读盘点

不改任何文件，先收集：

- 现有 Markdown 清单，按目录分组
- 现有 `docs/` 树（若有）
- 现有的 `AGENTS.md` / `CLAUDE.md` / `.cursorrules` 等 AI 配置文件
- 由外部工具写入的目录（识别出来即可，不要动）
- 现有 frontmatter 的字段形态

## 第二步：出四类方案

把盘点结果整理成四张表，交给用户：

| 类别 | 含义 |
|---|---|
| **保留原地** | 位置合理，只需补 frontmatter 或纳入索引 |
| **建议移动** | 位置与职责不符，给出目标路径与需要修复的链接 |
| **建议合并或废弃** | 内容重复、已被取代、或明显过期 |
| **明确不管** | 外部工具目录；列入 `docs/README.md` 的「不纳入索引的目录」 |

每一条都要给出**理由**。用户要能看懂"为什么要动它"，否则只会全部拒绝或全部同意——两种都不好。

## 第三步：逐项确认

用户确认哪几项，就只做哪几项。没有确认的一律不动。确认过程允许用户修改方案，改完再执行。

## 第四步：执行

按顺序做，每一步都可独立验证：

1. `git mv` 移动（不用 `rm` + 新建，否则丢失历史跟随）
2. 修复受影响的相对链接——**全局搜索旧路径**，不要只看被移动的文件
3. 按 `metadata.md` 的映射表补 frontmatter
4. 建立或更新目录 `README.md`
5. 把「旧路径 → 新路径」映射表写进 `docs/README.md` 末尾的「历史路径映射」一节

## 第五步：校验与报告

运行结构校验（见 `SKILL.md` 的自检一节），确认不引入新问题，然后报告改了什么、为什么改、还有什么留待处理。

## 安全铁律

以下每条都不可协商：

1. **不覆盖、不改写任何已有正文。** 已有内容只能被追加、被移动、或经用户明确同意后被改写。
2. **不移动或重命名未确认的文件**；移动必须走 `git mv`。
3. **已有 `AGENTS.md` / `CLAUDE.md` 一律追加合并，绝不替换。** 很多项目在里面放了自定义约束，替换掉等于静默删除用户的工作。
4. **不建空目录、不建占位文档。**
5. **外部工具目录识别但不动。**
6. **目标文件已存在就停下报告**，不静默跳过、不静默覆盖。
7. **迁移前要求工作区干净**（`git status` 无未提交改动）。不干净就先让用户提交或 stash——在有未提交改动的工作区上做文件移动，一旦出错无法回退。

> 违反规则的字面意思就是违反规则的精神。"我遵循的是精神"不是例外。
