# 根 README

> 何时读本文：要写或重写项目根 `README.md` 时。

## 定位：产品门面，不是设计文档

根 README 面向**刚到仓库的人**——可能是想用这个项目的人，也可能只是路过。
它要在几秒内回答三件事：**这是什么、能干什么、我怎么开始用**。

它不负责讲架构、不负责讲规范、不负责罗列模块。**写得像设计文档是它最常见的失败方式**：
读者看完知道了你的目录结构，却仍然不知道要不要用它。

## 可用的表达元素

以下是成熟开源项目里反复出现的元素，按需取用，不是清单：

| 元素 | 解决什么 | 备注 |
|---|---|---|
| **居中头部块** | 品牌感，让顶部不像随手写的 | 包住标题、定位句、徽章与多语言链接 |
| **一句话定位** | 替代"本项目是一个……"式的开场白 | 紧跟标题正下方 |
| **徽章** | 版本、构建状态、许可、下载量 | 每个都要有信息量，装饰性徽章是噪音 |
| **多语言 README 列表** | 方便非中文读者找到对应版本 | 只有确实维护了其他语言版本时才加 |
| **Logo / 通栏大图 / 截图** | 让人一眼看懂这是什么 | 越早越好；应用类项目常放在最顶部 |
| **锚点导航行** | 长 README 的目录 | 章节超过 6 个时加 |
| **emoji 章节标题** | 视觉分隔，扫读时好找 | 项目内风格统一即可 |
| **表格** | 能力矩阵、平台支持、对比 | 比一堆 bullet 好读得多 |
| **`> [!NOTE]` 提示块** | 前置条件、易踩的坑 | 支持它的平台会渲染成提示框，不支持的退化成普通引用块——不会坏 |
| **演示 GIF** | 降低理解成本 | 交互类项目收益最大 |

## 推荐结构

这是这类 README 的常见骨架。**除开头几项外，其余都按项目实际情况增删。**

```
居中头部：标题 + 一句话定位 + 徽章（可选）+ 多语言 README 列表（可选）
    ↓
一句话介绍 + 截图 / 演示图
    ↓
项目介绍（一到两段）
    ↓
核心功能
    ├─（可选）目录说明
    └─（可选）架构概览
    ↓
快速开始
    ├─ 运行环境
    └─ 安装与运行
    ↓
文档
    ↓
（可选）贡献 / 社区 / 致谢 / 许可
```

**居中头部**——标题与定位句是主体；徽章、多语言链接都属可选，没有就删掉。

**一句话介绍 + 截图**——截图紧跟介绍，越早越好。应用类项目常把通栏大图放在最顶部。

**项目介绍**——一到两段。讲清"这是什么、为谁解决什么问题、和同类有什么不同"。
不要在这里讲技术选型和实现原理，读者还没到关心那个的阶段。

**核心功能**——3–8 条，每条一句话。说"能做什么"，不说"用了什么技术"。其中可选包含两个子节：

- **目录说明**：只解释需要解释的顶层目录，一句话一个。不要贴完整目录树。
- **架构概览**：几句话说清分层或主要组件及其关系，能配一张图更好。

这两节内容不多就留作子节；内容变多、需要展开时升格为同级小节。详细设计属于
`docs/development/architecture/`，不要搬进来。

**快速开始**——分两步：先列运行环境（前置条件一句话一条），再给一段能直接复制执行的命令。
完整部署指南属于 `guides/user/`。

**文档**——一次跳转到 `docs/`，不在这里索引文档。

**其后**——贡献、社区、致谢、许可等，按项目实际情况增删。

**「快速开始」要足够靠前。** 包页与仓库首页只渲染开头几屏，把安装命令压到最下面的 README
等于没有快速开始。

## 居中头部骨架

三种常见写法，任选。示例里的 `{许可证标识}` 一类是**待填占位**——
不要照抄任何具体值：许可证、版本号、徽章服务、托管平台都由项目自己决定。

**用 `div` 包裹**（最灵活，可在内部再用 markdown）：

```html
<div align="center">

# 项目名

**一句话说明这是什么、给谁用**

[![License](https://img.shields.io/badge/license-{许可证标识}-blue.svg)](LICENSE)

<!-- 只有确实维护了其他语言版本时才加这一行 -->
[简体中文](README_zh.md) ｜ [English](README.md)

[核心功能](#核心功能) · [快速开始](#快速开始) · [文档](docs/README.md)

</div>
```

**用 `p` / `h1` 的 align 属性**（兼容性更广——部分渲染器**不在 HTML 块内部解析 markdown**，
用 `div` 包住 `# 标题` 时标题可能不生效，这种写法没有该风险）：

```html
<h1 align="center">项目名</h1>

<p align="center">一句话说明这是什么、给谁用</p>

<p align="center">
<a href="链接">外部站点</a> · <a href="链接">在线演示</a>
</p>
```

**只让徽章居中**，标题保持普通 markdown——适合不想太"营销"的技术项目。

## 按项目性质调整

同样是根 README，形态差别很大：

| 项目性质 | 形态 |
|---|---|
| 开源库 / 工具 | 徽章 + 快速开始 + 核心功能矩阵，克制；重点在"怎么装、怎么用" |
| 应用 / 平台 | 顶部大图 + 定位 + 能力列表，偏产品；重点在"能做什么" |
| 内部工具 | 可以只有定位 + 快速开始 + 指向 `docs/` 的链接 |
| 个人项目 | 允许个性（结尾一句话、一张 GIF），但开头三件事不能少 |

**不要为了"完整"而套用别人的全部元素。** 一个 CLI 工具不需要通栏大图和社区板块。

## 常见的走偏方式

| 走偏 | 后果 |
|---|---|
| 写成设计文档：大段罗列架构、模块、完整目录树 | 使用者看不懂，也无法判断"我要不要用它"。简要的目录说明与架构概览可以有，展开的设计属于 `docs/` |
| 一上来讲原理或背景 | 读者还没决定要不要用，讲原理太早 |
| 快速开始埋在最后 | 包页只显示开头几屏，等于没写 |
| 徽章堆一排纯装饰 | 无信息量的徽章稀释掉有信息量的 |
| 抄一份 `docs/` 的内容进来 | 两处要同步维护，必然分叉 |
| 核心功能列到十几条 | 等于没有重点 |
| 留空标题或"待补充" | 立刻显得项目不成熟 |

## 与其他文档的分工

| | 根 `README.md` | `docs/README.md` |
|---|---|---|
| 读者 | 刚到仓库的人 | 已经决定读文档的人 |
| 回答 | 这是什么、怎么跑起来、去哪找更多 | 文档怎么组织、元数据规范、事实源优先级 |
| 索引 | **不索引文档**，只一次跳转到 `docs/` | 索引整个 `docs/` |

根 README 一旦也列文档清单，就有了两处需要同步维护的索引，而且必然会分叉。

## 更新时机

- 对外能力变化 → 更新「核心功能」
- 安装或运行方式变化 → 更新「快速开始」与「运行环境」
- 定位变化 → 更新开头那句话

不需要为了每次功能迭代去动它。**它描述的是项目当前的样子，不是变更日志。**
