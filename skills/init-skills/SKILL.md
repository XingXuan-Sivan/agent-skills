# Skills 环境初始化向导

## 概述

本 Skill 是一个**元技能（Meta Skill）**，帮助用户在任何 AI Agent 软件中快速初始化 Skills 环境。推荐内容来自本目录 `resources/` 下的两份推荐清单；每个 Skill 的**安装源**通过 [skills.sh](https://skills.sh) 聚合平台检索获取。清单覆盖不到的需求，再用 skills.sh 的实时检索补充。

核心思路可以概括为：**读清单分层推荐 → 不够时 skills.sh 实时补充 → 用户确认 → 执行安装**。

## 核心原则

1. **skills.sh 驱动发现**：所有 Skill 的**安装源**检索、比对、推荐统一通过 skills.sh 聚合平台完成，本 Skill 不维护任何仓库地址。skills.sh 汇聚了数万 Skills，提供热榜、排行榜、分类浏览等维度，可根据用户场景动态匹配。**推荐哪些 Skill** 则由 `resources/` 下的两份推荐清单决定，清单可独立更新，无需改动本文件
2. **不擅自决定**：任何安装操作前，必须向用户清晰说明推荐理由、给出具体建议，**等待用户明确同意后再执行**。绝不替用户做选择
3. **层级由清单定义**：两份推荐清单里的类别按 `layer` 从小到大逐个推进，清单覆盖不到的需求再用 skills.sh 实时补充。**层数、类别名称与条目都以清单为准**，本文件不写死
4. **安装级别首次确认，全流程沿用**：安装级别（全局 / 项目级）在首次涉及安装时与用户确认一次即可，后续推荐沿用此偏好，无需重复询问。若用户后续主动提出不同级别需求，再个别调整
5. **平台无关**：所有平台差异信息外置于 `references/platforms.md`，路径与命令通过运行时动态探测
6. **CLI 优先**：`npx skills` CLI 是安装工具，若环境不满足优先引导用户配置，仅当用户明确拒绝时才降级到手动方式
7. **自然语言交互，示例引导**：与用户的交互以自然语言为主，避免僵化的 `[1][2][A][B]` 编号选项堆砌。必要时可以用编号辅助展示以增加清晰度，但始终提供**示例回答**让用户知道如何回应，鼓励用户以开放方式描述需求。如果当前平台自带动态交互组件（如按钮、复选框、`AskUserQuestion`），**是否用它来引导安装由你判断**——用与不用都行，判断依据见下面的「推荐交互的通用要求」
8. **灵活适配，拒绝死板**：推荐内容应根据用户实际需求和场景动态调整，而非机械罗列固定清单。推荐清单（`scenario-recommendations.json`）仅作参考基线，实际推荐时应结合 skills.sh 实时排行与用户具体情况灵活组合，不可照搬。同一决策不反复确认，但不同性质的新决策仍需征求用户意见
9. **重复安装检查**：安装任何 Skill 前，先通过 `npx skills list` 检查目标 Skill 是否已安装。若已安装，向用户说明其当前安装级别（全局/项目），询问是否需要调整级别（如从项目级提升到全局），若无需调整则跳过该 Skill，避免重复安装
10. **前置条件自检**：Skill 声明的前置条件不等于当前环境已经具备。安装前后都要按该 Skill 自己声明的依赖做一次实测——安装前用结果告诉用户「装上能用到哪些能力、缺了会少哪些」，安装后写进执行报告。缺失是常见情况，不是错误，但要让人知道

## 推荐交互的通用要求

分层推荐时，具体措辞、顺序和呈现方式由你按用户的语言、场景和当前平台自行组织，**不必套用固定句式，也不要照搬固定结构**。但每个候选都要落到下面几件事上，缺一件用户就没法判断：

- **它能做什么**：一句话说清解决的问题。取自清单条目的 `description`、`install_note`，或该 Skill 自己的说明，转成用户能懂的说法，不要照抄原文
- **为什么推荐给它**：和第一步了解到的场景怎么对上，哪些可能用不上
- **要付出什么**：条目 `requires` 里声明的前置条件、安装体积、需要的凭据或账号，以及缺失时会少掉哪些能力
- **怎么回应**：让用户知道可以怎么表达选择（要哪几个、全都要、先跳过），不强迫按编号勾选

同一层里各条目的详细程度应大体相当，不要只给其中一个写长段而其余只留名字。

**关于平台自带的选项组件**：当前平台自带按钮、复选框、`AskUserQuestion` 这类交互组件时，**用不用、用在哪一步、用来引导哪个环节，都由你自己判断**。它们适合让用户在已经列清的候选里做勾选；如果用户的需求还没收敛、或者你希望他自己描述，用自然语言问更合适。用了也要允许用户绕开选项直接说话，不要因为给了选项就把回答限制在选项内。

之所以只在此处写要求、不在各层写死话术：清单条目本身会变，写死的文案一旦对不上条目，就会同时误导用户和维护者。

## 执行流程

### 第零步：准备（环境与平台）

先做完环境检查和平台检测，再进入推荐。

#### 环境检查

在执行任何安装操作之前，**必须先检查 `npx skills` CLI 是否可用**。

1. 检查 Node.js 是否安装（≥18）：执行 `node --version`
2. 检查 npm/npx 是否可用：执行 `npm --version`
3. 检查 `npx skills` CLI 是否可用：执行 `npx skills --help`

#### 环境不满足时的处理

若任一检查失败，向用户清晰说明缺失项并引导决策。**交互应自然灵活**，不要用死板的编号选项堆砌。说明时至少要落到这几件事上：

- 缺了什么、当前是什么情况（例如「Node.js 未安装」或「版本过低，当前 vX.X.X」）
- `npx skills` CLI 在 Skills 生态里的作用，以及不配 CLI 的代价——改走 git clone / 手动下载 ZIP，且用不了 skills.sh 的搜索与热榜
- 你能代劳到什么程度：可以按 `references/platforms.md` 自动安装 Node.js 并在装完后验证，也可以就此跳过

具体措辞由你按用户的语言与上下文组织。用户无论怎么选，都按下面对应的一条走：

- **用户同意配置**：按照 `references/platforms.md` 中对应操作系统的指引自动安装 Node.js，完成后执行 `npx skills --help` 验证可用性
- **用户拒绝配置**：尊重选择，跳过 CLI，后续安装使用 git clone 或 ZIP 方式，并在最终报告中提示 CLI 缺失的影响
- **用户有其他想法**（如自行安装、已安装但路径不对等）：灵活应对，不要僵化套用预设选项

#### 平台检测

1. 询问用户当前使用的 Agent 软件，或通过工作区目录自动推断（`.qoder/`、`.claude/`、`.cursor/` 等）
2. 查阅 `references/platforms.md` 确认该平台的 Skills 目录路径
3. 记录平台信息。安装级别留到第一次安装前与用户确认一次，之后整轮沿用

### 第一步：了解用户需求

在推荐任何 Skill 之前，先简短了解用户的使用场景。交互应开放、自然，**不要把场景列举成死板的选项**，而是引导用户自由描述。这一问至少要拿到两件事：平时主要用 Agent 做什么（可以举一两个场景当引子，但不要变成多选题），以及有没有优先想装的类型或早已听说过的 Skill。问法由你按用户的语言自行组织。

根据用户回答，标记后续推荐策略的侧重点和优先级。

### 第二步：按层推荐与安装

**推荐什么不在本文件里，在两个清单里**。这两个清单合起来定义全部层级与条目，本文件只规定「怎么推」：

| 清单 | 内容 |
|------|------|
| `resources/recommended.json` | 基础元技能层（类别 `meta`），任何场景都建议装 |
| `resources/scenario-recommendations.json` | 场景类别集合，每个类别带 `name`、`description`、`layer`、`skills[]` |

条目上的 `description`、`required`、`keywords`、`requires`、`pairs_with`、`post_install`、`install_note` 就是推荐时要说清的全部信息，两份清单顶部的 `field_notes` 给出各字段语义，`presets` 给出按场景打包的类别组合（最小 / 标准 / 开发者 / 完整）。

清单会独立更新，**类别数量、名称与条目都可能变，不要照搬本文件里的任何条目名或层数**，每次都以读到的清单为准。

**推进顺序**：把两份清单里的所有类别放在一起，按 `layer` 从小到大排序，逐个类别推进；`layer` 相同的类别可以合并成一次推荐。

**对每一个类别，按下面的循环走一遍**：

1. **判断要不要推**：结合第一步了解到的场景。`always` 为真的类别（基础元技能层）对所有用户都推；其余类别整层用不上就跳过并说明原因（例如用户完全不涉及开发，面向开发者的类别可以直接跳过）。
2. **清单打底**：`required` 为真的标为必装，其余按 `keywords` 与用户场景的匹配度取舍，说明哪些最匹配、哪些可能用不上，不要机械罗列全部。互为替代的条目（见 `pairs_with`）按场景二选一。
3. **必要时补一次实时检索**——这是**可选动作**，只在下面两种情况触发，不要每个类别都做：
   - 该类别清单里没有能匹配用户场景的条目；或
   - 用户明确问了这个方向，而清单里的条目答不上来。

   触发时访问 skills.sh，取当前热榜与排行榜，与用户需求交叉筛出 5–8 个候选。这些候选按「推荐交互的通用要求」呈现，并额外给出**来源**（skills.sh 排名 / 热榜位置 / Star 数）与**质量信号**（更新频率、维护状态）。清单里的条目与检索来的候选放在一起比较，不要因为检索到新的就把清单条目挤掉。
4. **讲清代价**：按「推荐交互的通用要求」把每条的前置条件、体积、凭据说清楚。
5. **等用户确认再装**：按「安装方式」一节执行，装完后报告本类别结果，再进入下一个类别。

**全部类别走完后收一次尾**：如果用户还有清单和各层都没覆盖到的需求，做一次实时检索补上（做法同上面第 3 点）；没有就跳过。

**呈现格式**：表格是合适的载体，下面只是**格式示例**，列名可按平台与类别调整，内容一律取自清单：

| Skill | 用途 | 典型场景 | 前置/配置 | 建议 |
|-------|------|---------|----------|------|
| `<name>` | 条目的 `description`（转成用户能懂的说法） | 条目的 `keywords` 里最贴近用户场景的几个 | 条目的 `requires`，无则写「无」 | 必装 / 推荐 / 可选 |

表格前用一两句话交代这个类别是什么、为什么现在推它；表格后说明缺哪个前置条件会少掉哪些能力。条目少的类别（如基础元技能层）列名可以简化。**第一次推荐时一并确认安装级别**（全局 `-g` / 项目级），说清差别并给出你的推荐，之后整轮沿用。

### 第三步：输出执行报告

以一份「Skills 环境初始化报告」收尾，要说清下面这些内容；具体排版、顺序和措辞由你按用户的语言和当前平台组织，不必套用固定模板：

- **Skills CLI 环境**：Node.js、npm、`npx skills` CLI 各自的检测结果
- **平台信息**：Agent 软件，以及该平台的 Skills 全局目录与项目目录
- **安装结果**：逐个列出 Skill 名称、安装级别、安装方式、是否成功
- **前置条件自检**：本次所装 Skill 声明的前置条件，各自的类型、是否已具备、缺失时会少掉哪些能力。若所装 Skill 都没声明前置条件，这一节可以省略
- **数量小结**：本次新增多少个 Skill，其中全局安装与项目级安装各多少
- **注意事项 / 后续建议**：例如怎么查看已装 Skill、以后需要新 Skill 时怎么找

## 常用命令参考

在报告末尾附上这份参考。若用户在本次初始化中配置了 CLI 环境，作为"上手引导"；若未配置 CLI，作为"未来参考"：

```
## npx skills CLI 常用命令

`npx skills` 是 Skills 生态的包管理器。常用命令如下：

### 查找 Skills
  npx skills find <keyword>        # 按关键词搜索 Skill
  示例：npx skills find database   # 搜索数据库相关 Skills

### 安装 Skills
  npx skills add <owner>/<repo>@<name>       # 安装指定 Skill（项目级）
  npx skills add <owner>/<repo>@<name> -g    # 全局安装
  示例：npx skills add some-owner/some-repo@some-skill -g

### 查看已安装
  npx skills list                  # 列出所有已安装的 Skills

### 初始化项目
  npx skills init                  # 在当前项目创建 Skills 目录

### 获取帮助
  npx skills --help                # 查看完整命令列表

### skills.sh 平台
  浏览器访问 https://skills.sh —— 浏览热榜、排行榜、按分类检索 Skills
```

若 CLI 未配置，额外提示：
> 以上 CLI 命令需要 Node.js 环境。你可随时重新运行本 Skill 配置 CLI，或参考 `references/platforms.md` 中的环境配置指南。skills.sh 平台则无需 CLI，浏览器直接访问即可。

## 安装方式（多级降级）

具体命令与路径见 `references/platforms.md`。**每个类别的安装都走这一套流程，各层不再重复。**

**安装前**

1. **重复检查**：`npx skills list` 看目标是否已安装；已装则告知当前级别并询问是否调整，无需调整就跳过
2. **前置条件**：对照条目的 `requires` 实测环境（方法见「前置条件自检」），缺项时说明会少掉哪些能力，由用户决定补齐还是先跳过
3. **安装级别**：全局（`-g`）还是项目级。**第一次安装前与用户确认一次，之后整轮沿用**，除非用户主动调整
4. **取源**：`npx skills find <name>` 或访问 skills.sh，拿到最新的可用安装源

**安装**（按优先级降级）

1. **`npx skills` CLI**（首选）：`npx skills add <source>@<name>`，全局安装加 `-g`
2. **`git clone`**（CLI 不可用且用户拒绝配置时）：克隆仓库后手动复制 Skill 目录
3. **手动 ZIP 下载**（兜底）：按 `references/platforms.md` 的指引手动放置

条目带 `install` 字段时，按其 `command` 执行、装完用 `verify` 验证，覆盖上面的默认路径。

**安装后**

1. 条目带 `post_install` 的，提示用户在项目内完成该动作
2. 按「前置条件自检」再实测一次
3. 报告本类别结果，再进入下一个类别

## 前置条件自检

Skill 声明的前置条件，描述的是**该 Skill 作者所在运行环境**的现状，换一个 Agent 应用或换一台机器就不一定成立。技能文档里 `preinstalled` 一类的措辞尤其如此——它说的是「在我那套环境里已经装好了」，不是在你的环境里。所以前置条件要实测，不能凭印象。

自检对象是**本次要装或刚装完的每一个 Skill**，依据它自己声明的依赖：推荐清单里的条目看 `requires` 字段，清单外的 Skill 看其 SKILL.md 里列出的依赖。没有声明依赖的 Skill 不需要检。

**要检的三类**

- **运行时**：解释器与版本、外部命令、语言库
- **凭据**：账号授权、API Key、OAuth
- **服务**：本地端口或后台服务

**怎么检**

- 外部命令用 `where <命令>`（Windows）或 `command -v <命令>`（macOS / Linux）确认能否解析到，再用 `<命令> --version` 比对版本要求
- 语言库实际 import / require 一次。**多个解释器并存时尤其要确认用的是哪一个**——PATH 上的 `python` / `node` 未必是 Skill 期望的那个，两者的库集合可能完全不同
- 凭据只确认「是否已配置」，不读取、不回显其内容
- 拿不准某项算不算前置条件时，以 Skill 自己的声明为准，不要替它推断

**怎么用结果**

- **安装前**：把缺失项翻译成能力差异告诉用户——缺了会少哪些功能，让用户决定补齐还是先跳过
- **安装后**：把实测结果并入第三步的执行报告
- **复检时机**：换机器、换 Agent 应用、或 Skill 更新之后

部分 Skill 的脚本对操作系统或写权限有额外假设（例如依赖 POSIX 特性、需要把脚本写进自身目录）。遇到「安装成功但运行失败」，先怀疑环境差异，再怀疑 Skill 本身；也不要只看退出码，以产物真实打开的结果为准。

## 安全提醒

在安装任何第三方 Skill 前，提醒用户注意：
- skills.sh 聚合平台上的 Skill 来自公开 GitHub 仓库，安装前建议查看其 Star 数、更新频率和社区反馈
- 优先选择 skills.sh 上排名靠前、更新活跃的 Skill
- 安装前通读 SKILL.md，确认操作范围在预期之内
- 安装前对照推荐清单条目的 `requires` 字段，确认运行时依赖（如 Node.js 版本、LibreOffice）、凭据（如账号授权、API Key）和本地服务是否已具备；凭据一律由用户自行配置，不要写进 Skill 文件或提交到版本库
- 避免使用超过 6 个月未更新的 Skill
- 详细安全评估指南见 `references/security.md`
